## THE BIG IDEAS (what the whole curriculum orbits)

1. **The harness > the model.** "Agent = model + harness." Life-Harness paper (arxiv.org/abs/2605.22166): 116/126 setups improved by patching the harness alone; 88.5% mean lift across 18 backbones. Same Sonnet 4.5 swings 31%→75% on GAIA from scaffolding alone. Harness = context management + tools + verification + memory + termination.
2. **Loop engineering is the new prompting.** Boris Cherny: "I don't prompt Claude anymore. I have loops... My job is to write loops." Loop = prompt → act → check against REAL criteria → decide done/not → re-prompt. The craft: making the check real and defining when to stop. Failure modes: no memory file, no subagent split, no stop condition ("bills you in your sleep").
3. **Context engineering ⊃ prompt engineering.** Attention budget / context rot (n² attention). Smallest set of high-signal tokens. Progressive disclosure / just-in-time retrieval. Compaction vs structured notes vs subagent isolation.
4. **Verification is the #1 quality lever.** Give the agent a binary pass/fail signal (tests, build, screenshot). Stop hooks block "claims done but isn't." Cherny: verification loop "2-3x the quality." Matt Pocock: write the failing test first.
5. **Files are the universal agent substrate.** CLAUDE.md, SKILL.md, DESIGN.md, spec.md, memory.md, filesystem-as-state ("Your Company is a Filesystem" — Eli Mernit). Markdown folders beat databases because they're legible to both humans and models.
6. **Classic engineering discipline became MORE valuable.** Specs, tests, CI, review are the control surface for agents (Willison's "vibe engineering", Karpathy's "vibe coding raises the floor; agentic engineering raises the ceiling").

### F. RAG (mid-2026)
- Pipeline: ingest → chunk (200-800 tok) → embed → vector store → hybrid retrieve (BM25 + dense + RRF) → rerank (cross-encoder) → generate w/ citations → evaluate (RAGAS, 50-200 real-query eval set).
- Embeddings: text-embedding-3-large / Cohere v4 / Voyage (hosted); BGE-M3, Qwen3-Embedding (open). Same model for index+query.
- Stores: pgvector (default w/ Postgres), Qdrant/Milvus (scale), Chroma (dev), Pinecone (managed).
- Agentic RAG = retrieval-as-a-tool inside agent loop (2026 default for hard cases): plan, multi-query, reformulate, mix tools.
- Decision rule: caching-backed long context (1M) for small stable corpora; RAG for big/fresh/permissioned; fine-tune for behavior not knowledge.
- Claude Code memory is keyword-only → memsearch-style semantic add-ons illustrate the gap.

### G. Fine-tuning
- LoRA (adapters, 0.1-1% params) / QLoRA (4-bit NF4 base): 8B tunes on 8-12GB; 70B on one H100 (~3 hrs).
- Tools: Unsloth (2-5× faster), Axolotl (YAML, multi-GPU, DPO/GRPO), HF PEFT+TRL, **MLX-LM on Mac** (`mlx_lm.lora --model ... --data ... --iters 1000`; Mistral-7B + 5k examples ≈ 90 min on M2 Max 32GB).
- Hosted: OpenAI WINDING DOWN fine-tuning API (verify); Together (LoRA $0.48-2.90/M tok by size), Fireworks (serves tuned at base prices). DIY: 8B QLoRA ≈ $0.44-0.88 on RunPod.
- Worth it: style/format/persona, classification/extraction, tool-call formats, cost/latency shrink, edge. NOT: knowledge injection (RAG), <500 examples, prompt-solvable.
- Distillation = dominant pattern: frontier teacher generates/grades data → QLoRA small open model. ToS: closed-model outputs restricted; open teachers (DeepSeek MIT, Qwen Apache) avoid it.
- Real cost = dataset curation + evals, not compute.

## ADDENDUM — August 26, 2026 batch (spec engineering)

Sources: Bill's own research screenshots (spec sizing + archiving), plus fresh web research 2026-08-26. Fed into m1-l9 (new "Inside the spec" section) and m7-l2 (maturity levels + limits).

- **Addy Osmani, "How to Write a Good Spec for AI Agents" (addyosmani.com/blog/good-spec/, also O'Reilly Radar):** analysis of 2,500+ agent config files. Six recurring areas in configs that worked: commands, testing, project structure, code style, git workflow, boundaries. **Three-tier boundary system** (Always / Ask first / Never) was the standout pattern; "never commit secrets" the single most common useful constraint. Also: "curse of instructions" (adherence per instruction drops as you pile them on), extended TOC for large specs, self-check appendices, conformance tests, LLM-as-judge review pass. Scale detail to task complexity ("center a div" needs no spec).
- **Allegro Tech, "Spec-Driven Development best practices (so far)" (blog.allegro.tech, June 2026):** three maturity levels spec-first / spec-anchored / spec-as-source, recommends spec-anchored. Must-contain vs should-contain vs avoid lists for spec bodies. Under-specification → agent interprets too broadly; over-specification → "the line between specification and code starts to blur and the specification loses its value." Risk-based detail level. **Separate what (spec, stable) from how (plan, volatile, discardable).** SHARED-TECHNICAL-SPEC.md for org-wide NFRs. One spec per feature for medium/large projects. TDD/BDD as executable acceptance criteria; fresh-context agent review after implementation. Internal orchestrator "AlleManager" fans out to AllePlanner/AlleTester/AlleCoder/AlleReviewer/AlleSpecUpdater.
- **"Spec-Driven Development in 2026" (dev.to/krlz):** canonical 7-phase flow Constitution → Specify → Clarify → Plan → Tasks → Implement → Analyze. Tooling map: GitHub Spec Kit (reference, model-agnostic), AWS Kiro (AWS shops), cc-sdd (Claude Code CLI), Cursor Plan Mode, OpenSpec (minimal), Tessl (regulated). Worked magic-link example with tasks citing spec clauses (traceability). Failure modes: over-specification, false confidence from a correct build of a wrong spec. Skip SDD for throwaway prototypes, solo short-lived work, exploratory work. **Thoughtworks Radar puts SDD in "Assess", not "Adopt";** Brandon Kindred's critique: "largely waterfall/contract-design rebranded... the value is the thinking you do while writing the spec, not the tooling."
- **EARS (alistairmavin.com/ears/):** Easy Approach to Requirements Syntax, five patterns — ubiquitous ("The system shall X"), event-driven (WHEN), state-driven (WHILE), unwanted behavior (IF/THEN), optional feature (WHERE). Now the default acceptance-criteria format in Spec Kit and Kiro. Each line maps ~1:1 to a test case, which is what makes it worth teaching: it produces the binary verification signal m1-l9 already demands.
- **Numbers to treat as directional (vendor/blog claims, unaudited):** GitHub reports ~an order of magnitude fewer "regenerate from scratch" cycles with Spec Kit on internal projects; "error reductions on the order of tens of percent" from refined specs vs loose prompts; the widely repeated "an extra hour on the spec saves three days of agent thrash" is a rhetorical figure, not a measurement. Lessons state the mechanism, not these numbers.

## PARALLEL WORK & INTEGRATION (researched 2026-08-27, for m1-l11 Landing Parallel Work)
- **arXiv 2607.04697, "AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict Rates" (July 2026):** 33,596 agent-authored PRs across 2,807 repos. 40.2% of repos had temporally overlapping agent PR pairs, covering 79.4% of all agent PRs (one-week window: 53.4% / 95.0%). Textual conflict rate: cross-agent pairs 41.7% vs intra-agent 19.8%, non-overlapping 95% CIs. 84.4% of conflicted files were source code (not deps/lockfiles); ~42% of conflicts structural (modify/delete, add/add). Cross-agent pairs were only 0.5% of co-active pairs, in 4.3% of repos. THE anchor stat for the lesson.
- **Claude Code native worktrees (code.claude.com/docs/en/worktrees):** `claude --worktree <name>` / `-w` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`. Setting `worktree.baseRef`: `"fresh"` (DEFAULT) branches from remote default branch, fetching if >24h stale, capped 5s, falls back to local HEAD if no remote; `"head"` branches from local HEAD (use for subagents on in-progress work). Can't be set to a branch name. `.worktreeinclude` (gitignore syntax) copies gitignored files like .env into every new worktree. `--worktree "#1234"` branches from a PR/MR head. Isolation is ENFORCED: edits to the main checkout, cwd escapes, git redirects (-C, --git-dir, GIT_DIR), and untraceable shell shapes are all blocked. Subagent `isolation: worktree` frontmatter uses the same base. Periodic sweep cleans subagent/background worktrees per cleanupPeriodDays; keeps any with work or without Claude's marker. Desktop app: every new session gets its own worktree automatically. Docs page covers NONE of the merge-back question, which is the gap m1-l11 fills.
- **Integration doctrine (Augment Code multi-agent workspace guide; Autonoma "5 Ways to Stop AI Agents Stepping on Each Other"):** parallel generation, SEQUENTIAL landing. Rebase each branch onto the newest main, then merge, then gate, then next. Frozen base snapshot for all parallel agents. Scope agents to non-overlapping work units with named file ownership up front. Hotspot registry (auth, migrations, shared config, API contracts) triggers mandatory human review regardless of CI. `git merge -X patience` / ort = diff-quality tool, explicitly NOT a correctness proof.
- **Semantic conflicts:** the load-bearing concept. A green + B green, A+B red, with git reporting a clean merge. Documented failure: an agent resolving a conflict "knows neither side's intent, sees the diff and picks the version that looks more recent, more complete, or more syntactically coherent" so the losing feature silently ceases to exist (no error, no failing test). Prevention is behavioral verification after EACH merge (log in as the restricted role and try the restricted thing), not unit tests, not syntactic analysis. Merge queues exist to give CI awareness that parallel branches may semantically conflict.
- **Stacked PRs (Graphite, git-spice), researched but NOT taught:** relevant to teams landing dependent changes; deliberately left out of m1-l11 to keep it about solo parallel agent work. Note if a team-workflow lesson ever gets written. Supporting stat: PRs under 200 lines get approved 3x faster; 200-400 line PRs show 40% fewer defects than larger ones.

## TEAM SHIPPING: STACKS & MERGE QUEUES (researched 2026-08-27, for m7-l3)
- **CircleCI 2026 State of Software Delivery (28,738,317 workflows, Sept 2025):** feature-branch throughput +15% for the median team, main-branch throughput -7%. Main-branch success rate 70.8%, lowest in 5+ years vs CircleCI's own 90% benchmark. Median recovery time 72 min, up 13% YoY. Top-10% teams: ~50% feature-branch growth, only 1% main-branch increase. Report's own framing: writing code stopped being the constraint; review/validation/integration/recovery is.
- **LinearB 2026 Benchmarks (8.1M PRs, 4,800 teams, 42 countries):** merged within 30 days: human 84.5%, AI-assisted 32.7%. PR size p75: human 157 lines, AI 400+ (~2.5x). Pickup time before review starts: AI >16 hours vs ~200 min human (5x+). Once review starts AI is FASTER: 194 min vs 252. Refactoring share at p75: human ~37%, AI near zero (agents write new code, not debt paydown). 88.3% of devs use AI regularly, up from ~72% early 2024.
- **Mergify State of Merge Queues 2026 (200k+ merges, 477 orgs, 160 with active queues, rolling 90 days):** broken-main by team size: 2-5 eng 0.77% (1 in 130), 6-15 0.98% (1 in 102), 16-40 2.49% (1 in 40), 40+ 12.5% (1 in 8). Median time in queue 8 min private / 5 min OSS; p90 63 min / 68 min. Median 3.1 merges per active day; busiest repos 30+/day. Batching adoption only 6% of private merges. Private vs OSS broken-main 5.1% vs 1.1%. AI-assisted PRs broke main LESS: 1.9% vs 4.4%, at 137 avg changed lines vs 84.
- **THE TENSION WORTH TEACHING:** LinearB (AI PRs merge at 32.7%) and Mergify (AI PRs break main less, 1.9% vs 4.4%) are both right. Review is the filter. The agent PRs that survive are solid; the cost is the two-thirds that stall unread. Taught explicitly in m7-l3 rather than cherry-picked.
- **GitHub merge queue mechanics:** speculative merge commit = PR on top of current main tip, a combination neither CI run tested; required checks run against THAT; main fast-forwards only on green. Batching: max group size N tested as one commit. Min group size + wait time (e.g. hold up to 5 min to collect 3 PRs). Bisection on batch failure is AUTOMATIC, not configurable: split, retest halves, eject the culprit, pass the rest. CI math: 20 merges/day at 30-min pipeline = 10h serial vs 2.5h at batches of 4 (75% cut).
- **Stacked PRs:** stack = chain of branches each based on the one below, each its own PR. Merge bottom-up; restack (rebase dependents onto updated base) after each merge. Tools: git-spice (free CLI, `gs repo init` / `gs branch create` / `gs stack submit` / `gs stack restack` / `gs repo sync`; supports GitHub, GitLab, Bitbucket, Gitea, Forgejo) and Graphite (hosted, review UI, automations for reviewer routing more granular than CODEOWNERS). GitHub settings that break stacks: "dismiss stale approvals" and "require approval of the most recent reviewable push" both nuke approvals on upper PRs whenever a lower one changes. PR size research: <200 lines approved ~3x faster; 200-400 lines ~40% fewer defects than larger.
